재설계 원칙 — ECRS + A

자동화는 마지막 순서입니다

ECRS

네 가지 질문, 네 가지 원칙

원칙질문한 줄 예시
E — Eliminate 제거이 단계, 없애도 되는가?중간 결재 라인 폐지, 중복 보고서 통폐합
C — Combine 결합나눠진 것을 합칠 수 있는가?3개 시스템 입력을 한 번으로, 검토+승인 병합
R — Rearrange 재배열순서·담당을 바꾸면 나은가?사후 검토 → 사전 검증, 병렬 처리
S — Simplify 단순화더 쉽게 만들 수 있는가?양식 항목 축소, 선택지 표준화
그리고 A — Automate위 네 가지로 먼저 줄이고, 남은 것에만 자동화를 적용합니다. 순서가 바뀌면 "소 길 포장"이 됩니다.

Order Matters

왜 "먼저 단순화, 나중에 자동화"인가

🚫 자동화부터 한 경우

  • 쓸모없는 보고서가 매일 자동 생성됨
  • 복잡한 예외를 AI가 그대로 학습 → 오류 확대
  • 통합 비용이 자동화 이익을 초과

✅ ECRS 후 자동화한 경우

  • 자동화 대상 자체가 절반으로 줄어듦
  • 남은 작업이 표준화되어 AI 정확도 ↑
  • 예외가 단순해져 HITL 설계가 쉬워짐

"단순화하지 않은 프로세스의 자동화는 비용이고, 단순화한 프로세스의 자동화는 자산이다."

Checklist

재설계 휴리스틱 10

  • 서명·승인 단계마다 "왜 필요한가"를 묻는다
  • 입력은 한 번만 — 재입력은 설계 결함이다
  • 검토는 사후가 아니라 진행 중에 넣는다
  • 예외는 유형화하고, 유형별 처리 경로를 만든다
  • 찾는 시간을 줄이는 데 투자한다 (검색·인덱스)
  • 대기가 긴 단계는 병렬로 풀 수 있는지 본다
  • 사람이 할 일의 단위를 "판단 1회"로 자른다
  • 규칙으로 표현되면 규칙 엔진, 맥락이 필요하면 AI
  • 모든 자동화에는 "사람에게 올리기" 버튼을 둔다
  • 측정하지 않은 단계는 재설계하지 않는다

Decide

배치를 결정하는 4가지 질문

질문예에 가까우면
데이터가 있는가과거 사례·로그가 풍부 → 자동화 후보
변동성이 낮은가규칙·유형이 안정적 → 자동화 후보
영향도가 높은가금전·안전·평판 리스크 → 사람 승인 필수
설명이 필요한가근거 제시·책임 소재 필요 → 사람 주도

"데이터 있음 + 변동성 낮음 + 영향도 높음" 조합이 가장 흔한 실전 영역이며, AI 수행 + 사람 승인 패턴이 정석입니다.

HITL

Human-in-the-loop 패턴 4가지

🚦 승인 게이트

AI가 안을 만들고, 임계값(금액·위험도) 초과 시 사람이 승인해야 진행됩니다.

🆘 예외 에스컬레이션

자신도 낮음·미분류 케이스는 자동으로 사람에게 라우팅되고, 처리 결과는 학습에 반영됩니다.

🔍 샘플링 감사

자동 처리 건 중 일정 비율을 사람이 표본 점검하여 품질 저하(드리프트)를 조기에 발견합니다.

🔁 피드백 루프

사람의 수정·반려 사유가 데이터로 쌓여 프롬프트·규칙·모델을 지속 개선합니다.

네 패턴은 조합됩니다: 평소 자동 → 임계값 초과 시 승인 게이트 → 주간 샘플링 감사 → 수정분 피드백.

Agentic Patterns Ⅰ

에이전틱 워크플로우 — 기본형

🔗 프롬프트 체이닝

작업을 고정 순서의 단계로 분해해 연결합니다. (분류 → 초안 → 검토)

언제: 단계가 안정적이고 순서가 분명한 업무

🚏 라우팅

입력을 분류해 각기 다른 처리기(템플릿·모델·사람)로 보냅니다.

언제: 문의 유형별로 최적 경로가 다른 CS·헬프데스크

설계 관점이 패턴들은 "AI를 부리는 법"이 아니라 프로세스의 단계를 정의하는 법입니다. ECRS로 정리한 단계 구조가 그대로 체인이 됩니다.
Agentic Patterns Ⅱ

에이전틱 워크플로우 — 확장형

⚡ 병렬화

독립 하위 작업을 동시에 실행해 취합합니다.

언제: 다건 검토, 다국어 처리

🧠 오케스트레이터-워커

중앙 에이전트가 계획을 세우고 워커들에게 위임·통합합니다.

언제: 단계 수를 미리 정할 수 없는 조사·분석

✅ 평가자-개선자

생성 → 평가 → 개선을 반복해 품질 기준을 맞춥니다.

언제: 보고서·번역 등 품질 기준이 명확한 산출물

절제 원칙에이전트 자율성은 단순한 것에서 시작해 검증 후 확장합니다. 체이닝으로 충분한 곳에 오케스트레이터를 쓰지 마세요.
Part 3

To-Be 설계 실전

절차 · 사례 · 가드레일

Procedure

To-Be 설계 6단계

  1. 낭비 매핑 — As-Is 단계별 낭비 이름을 확정
  2. ECRS 적용 — 제거·결합·재배열·단순화 후 남은 단계만 남기기
  3. 역할 배치 — 남은 단계를 2×2 매트릭스에 배치
  4. HITL 설계 — 승인 게이트·에스컬레이션 위치 결정
  5. 데이터·가드레일 — 입력 데이터, 정책, 감사 로그 정의
  6. 목표 지표 설정 — %STP·리드타임·반려율 목표치

Guardrails

자동화의 안전장치 4가지

📜 정책

자동화 가능 범위·임계값·금지 항목을 문서로 고정합니다. (예: "개인정보 포함 건 자동 발송 금지")

🔐 권한

AI 에이전트에도 사람과 같은 최소 권한 원칙을 적용합니다. 시스템 접근·금액 한도를 부여합니다.

🧾 감사 로그

입력·판단 근거·출력·승인자를 모두 기록해 사후 설명 가능하도록 합니다.

🪂 폴백

모델 장애·자신도 저하 시 자동으로 사람 큐로 전환되는 경로를 항상 열어 둡니다.

Data

데이터 전제조건 체크리스트

  • ☐ 과거 처리 이력(입력 → 결과)이 최소 수백 건 있는가
  • ☐ 입력 데이터의 형식이 표준화되어 있는가 (또는 표준화 가능한가)
  • ☐ 정답 라벨(승인/반려, 분류 결과)이 함께 기록되어 있는가
  • ☐ 예외·특수 사례가 이력으로 구분되는가
  • ☐ 개인정보·기밀 데이터의 마스킹 정책이 있는가
  • ☐ 데이터 접근 권한·감사 체계가 마련되어 있는가
실전 팁체크가 부족한 항목은 파일럿의 0주차 준비 작업으로 넣으세요. 데이터 없이 모델을 탓하는 것이 가장 흔한 실패입니다.

Pitfalls

재설계의 다섯 가지 함정

  • 과잉 자동화 — 영향도 높은 판단까지 무인화 → 사고 한 번에 신뢰 증발
  • 예외 무시 — 평균 케이스만 설계 → 운영이 예외 처리로 마비
  • 섀도 AI — 공식 절차 밖 개인 AI 사용 → 데이터·보안 사각지대
  • 조급한 자율성 — 검증 없이 에이전트 권한 확대
  • 지표 없는 재설계 — 개선 전후를 비교할 수 없어 성과 증명 실패
Summary

Module 3 요약

  • ECRS → Automate: 줄인 다음에 자동화한다
  • 2×2 매트릭스로 단계별 인간-AI 역할을 배치한다
  • HITL 4패턴(승인·에스컬레이션·감사·피드백)으로 안전을 설계한다
  • 에이전틱 패턴은 단순한 것부터, 절제해서 쓴다
  • 가드레일과 데이터 전제조건은 설계의 일부다
